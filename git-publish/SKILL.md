# Git Publish

## 发现仓库约定

先读取目标仓库适用的 AGENTS.md 和发布规则。分支、远端、合并方式、提交格式、检查及钩子均以目标仓库和用户授权为准，不预设 main/master/develop、GitHub 或特定语言。

从当前会话推导本次功能、文件及排除项。检查工作区、暂存区、当前分支、远端和相关提交：

```text
git status --short --branch
git diff --name-status
git diff --cached --name-status
git remote -v
git config --get core.hooksPath
```

远端 URL 若含凭据须脱敏。用户未指定目标时结合上游及仓库规则判断；只有无法可靠确定且会改变发布对象时才询问。用户要求指定客户端时使用该客户端，不能静默改用 CLI。

## 隔离任务范围

- 工作区已有改动、暂存内容和本地领先提交都需要判断归属；精确暂存不能阻止已有无关提交一起被推送。
- 对混合文件按 hunk 或受控 patch 暂存，不覆盖工作区、不清空无关暂存。不易分离时可在隔离工作副本组织交付，前提是符合仓库分支规则；仍无法确定归属时暂停相关提交并说明。
- 移动文件同时核对旧路径删除、新路径新增及重命名内容。临时产物只有属于用户交付范围才纳入。
- 用户明确要求全部改动时按该范围检查，不自行缩小；不要把“全部改动”解释为允许包含凭据或覆盖他人工作。

## 验证与整合

复用本任务已经通过且仍适用的验证。根据实际改动和仓库要求选择测试、编译、语法或文档检查，不套用固定技术栈，也不为单纯发布重复运行全部测试。

Fetch 目标分支，核对双方提交和领先/落后关系，例如 `git rev-list --left-right --count HEAD...<remote>/<branch>`。新远端分支不存在时核实创建意图及起点，不能把引用不存在当作已同步。

远端领先时判断是否可以安全快进；分叉时先检查双方内容，按仓库允许的策略整合。不要默认 pull --rebase、强推或改写共享历史。整合产生变化或冲突时重新运行必要验证。若推送被拒绝，先确认原因，再修复并重试；认证、权限或保护规则问题不能靠重复推送解决。

## 提交与交付

1. 按明确路径或 hunk 暂存，检查 `git diff --cached --name-status`、`git diff --cached --check` 和当前分支。
2. 只在用户授权时提交，遵循仓库提交格式。无改动不制造空提交；已有目标提交时可直接进入获授权的推送步骤。
3. 执行仓库要求的钩子。钩子失败先检查提交是否已经生成，避免重复提交；不要擅自跳过钩子。
4. 推送前再次核对实际源分支、目标远端与目标分支。受保护分支按仓库规定的合并或 PR 路径交付，不绕过保护；需要审批的路径完成可执行准备后再报告阻塞。
5. 推送后用 `git ls-remote <remote> refs/heads/<branch>` 读回，核对期望提交；PR 工作流区分“源分支已推送”“PR 已创建”和“目标分支已合并”。

每步检查退出状态。远端核对失败时如实区分提交、推送及核对结果。最终报告交付范围、提交 ID、目标、必要验证和剩余阻塞；工作区有无关改动时说明已保留。代码推送不等于文档平台同步或部署完成。
